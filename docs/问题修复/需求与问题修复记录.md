### 问题修复3：干预机制重构 — 从队列轮询改为 stop+resume
- **现象**：
  - v1: 干预按钮点了后当前步骤仍继续执行（轮询检查点延迟）
  - v2: `stopRequested` 导致任务被误终止，干预消息在队列中无人消费
  - v3: 增加检查点后仍无法保证立即中断（模型调用期间无法中断 HTTP 请求）
- **根因**：队列轮询 + 标志位检查的架构过于复杂，检查点分散在多处且无法覆盖阻塞式 HTTP 调用
- **重构方案**：彻底废弃 `interruptForIntervention`/`pendingInterventions` 队列轮询机制，改为 **stop + resume** 模式
  1. 点击 ✎ → `currentTaskJob.cancel()` + `phoneAgent.stop()` 立即杀掉协程（保留对话历史和服务状态）
  2. 弹出输入框等待用户输入
  3. 用户提交 → `phoneAgent.resumeWithIntervention(instruction)` 注入干预消息到对话历史 → 重新启动协调器/Agent 执行
- **优势**：立即中断（协程 cancel 秒级生效）、逻辑简单（无状态同步问题）、对话历史完整保留
- **删除的代码**：`interruptForIntervention`、`pendingInterventions`、`intervene()`、`requestInterventionInterrupt()`、所有干预检查点
- **新增的代码**：`PhoneAgent.resumeWithIntervention(instruction)` 方法
- **修改文件**：`PhoneAgent.kt`、`WakeWordService.kt`
- **状态**：✅ 已完成

### 问题修复4：干预后 agent 直接 finish 不执行纠正
- **现象**：用户干预后（如"送到当前位置"），agent 直接回复"已成功结束"而不实际切换地址
- **根因**：
  1. 对话历史末尾保留了 `finish(message="...")` 和任务总结，模型看到后误认为任务已完成
  2. 系统提示词无规则约束干预后行为
  3. 干预指令原文注入缺乏执行上下文，模型难以理解具体操作
- **修复**：
  1. **清理 finish 历史**：`resumeWithIntervention()` 注入干预前，从对话历史末尾移除最后一条 `finish(` 消息及之后的所有消息，避免模型误判任务已完成
  2. **prompt 规则**：中英文 agent 系统提示词新增第 22 条规则 —— 收到「用户干预」后必须实际执行调整操作，禁止直接 finish
  3. **干预优化**：`PromptOptimizer` 新增 `optimizeIntervention()` 方法，结合原始任务 + 已执行步骤上下文优化干预指令（优化器开启且指令>5字符时触发）
- **新增代码**：
  - `PromptKey`：`INTERVENTION_USER_CN`、`INTERVENTION_USER_EN`
  - `PromptRegistry`：干预优化 user 模板
  - `PromptOptimizer`：`optimizeIntervention()`、`buildExecutionSummary()`
  - `PhoneAgent`：`lastOriginalTask` 字段、干预优化调用逻辑
- **修改文件**：`PromptRegistry.kt`、`PromptOptimizer.kt`、`PhoneAgent.kt`
- **状态**：✅ 已完成

### 问题修复5：总结生成期间干预 → 干预进程被终止
- **现象**：任务完成后生成总结过程中用户点击干预，总结输出完后干预进程也终止了（状态被设回 IDLE）
- **根因**：竞争条件
  1. `generateTaskSummaryIfEnabled()` 的 `catch(e: Exception)` **吞掉了 CancellationException**，导致 cancel 信号被忽略
  2. 总结生成完后，`executeDirectly()` 继续执行 `onTaskComplete?.invoke()` → WakeWordService 把 `_serviceState` 设回 `IDLE`
  3. 干预流程虽然启动了新协程，但状态已被覆盖
- **修复**：
  1. `generateTaskSummaryIfEnabled()` 新增 `catch(e: CancellationException) { throw e }`，确保 cancel 正确传播
  2. `executeDirectly()` 和 `executeWithCoordinator()` 在调用 `onTaskComplete` 前检查 `stopRequested`，阻止已中断的任务触发完成回调
- **修改文件**：`PhoneAgent.kt`
- **状态**：✅ 已完成

### 问题修复6：Type 操作不清空已有文本（追加而非替换）

### 问题修复7：CLEAR_INPUT 广播成功但文本未清空

  3. 第三级兜底改为“光标移到末尾 + 批量 DEL 删除 + 复查剩余文本长度”
- **修改文件**：`ActionExecutor.kt`、`ShellExecutor.kt`

  2. 在总结生成前及各中止节点注入提前恢复 IME 的调用。
  3. `WakeWordService.kt`：`onDestroy()` 添加输入法恢复保障。

### 问题修复12：前台服务自启崩溃退出（Android 14 MediaProjection 权限）
- **现象**：加入自启逻辑后，应用打开时仍然显示为"语音唤醒未启动"。
- **根因**：（这个是被隐藏的雷）Android 14 要求带 `mediaProjection` 类型的前台服务必须在有相应的权限 Token 的上下文中被启动；直接后台开启会导致系统直接抛出 `SecurityException`，并且被通用捕获而立即调用 `stopSelf()` 默默销毁服务。
- **发现过程**：adb 日志只过滤 `AutoGLM`，而该类异常直接抛在了 `WakeWordService` 默认的 TAG 下，导致日志被隐藏。
- **修复**：修改了自启配置（在 `App.NOTIFICATION_ID` 中不在静默启动阶段强制挂载 `ServiceInfo.FOREGROUND_SERVICE_TYPE_MEDIA_PROJECTION`），移除该限制仅获取 microphone 和 task 处理的服务类型，随后成功在后台站住并且进入监听状态。
- **修改文件**：`WakeWordService.kt`
- **状态**：✅ 已修复

### 问题修复13：应用内启动失败（不需要悬浮窗）
- **现象**：在应用内明明已经启动了，但还是会要求给出悬浮窗权限，影响单纯在App内使用唤醒的体验。
- **原因**：`MainActivity` 强制校验了 `Settings.canDrawOverlays`。
- **解决方案**：将强制校验改为发 Warning 记录。用户可以直接在App内点击按钮启动唤醒，此时 `WakeWordService` 正常启动并在后续触发时显示半透明助手窗体，仅在外层展现时才存在一些限制，整体不再强阻断使用流程。

### 问题修复14：唤醒词被检测到后就闪退 / "权限不足"错误
- **现象**：当从后台状态唤醒时，STT报 "权限不足" 错误并立刻退出监听。
- **原因**：Android 11 以上系统禁止后台 Service 隐式启动自带的麦克风或 `SpeechRecognizer`。麦克风权限只允许在 UI Activity / Foreground 模式下发起。
- **解决方案**：修改了架构。服务在监听到唤醒词后，会使用FLAG_ACTIVITY_NEW_TASK呼出一个半透明无窗口样式的Activity：`AssistantActivity`。由这个Activity充当前台UI主体回调通知 Service 此时再进行 STT 启动。绕过了Android系统的隐式后台麦克风保护机制。
